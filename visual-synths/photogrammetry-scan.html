How it works

Structure-from-Motion. The scan was made from ordinary images, not a laser. An SfM solver (here AliceVision, the engine inside Meshroom) finds distinctive features in every frame, matches them across frames, then solves for the camera poses and the 3D feature positions together by minimising reprojection error — bundle adjustment. Each surviving match becomes one point; its colour is the pixel colour where it was seen. The result is a sparse cloud: dense where facades have texture, empty on glass, sky and flat roofs, which is why the towers read as lattices.

Getting the file onto the page. The export is an Alembic archive in its Ogawa binary layout — a tree of groups and data blobs addressed by 64-bit offsets. A small reader (in Python for the bundled file, and a JavaScript port on this page for the files you drop) walks that tree to the AbcGeom_Points object and reads P and color, then every camera transform. The bundled scan was converted once into a 2 MB binary (16-bit positions, 8-bit colour) — a quarter of the 8.5 MB original.

Which way is up. SfM recovers a scene only up to an unknown rotation, translation and scale — no gravity, no metres. The page takes the average "up" vector of all 251 solved cameras (people and drones hold the horizon level) as vertical, centres on the 1st–99th percentile box of the points so a few stray matches can't shrink the city, and scales it to the same 2.6-unit frame as the other studies. Use Up axis if a dropped file without cameras arrives on its side.

Capture path. The cameras are sorted by the frame number in their names, which recovers the original flight. Frames were sampled sparsely (about 11° of turn between neighbours), so the view rides a Catmull-Rom spline through the solved positions and blends the solved viewing directions between them. It uses the solved lens: a 26.6° vertical field of view. The white frustums show where each frame was taken.

Effects. Scan plane, drift and slice glitch are the same vertex-shader effects as Point Cloud Scan, run on measured points. Decompose works differently here: each point gets its own random release threshold, so the city comes apart everywhere at once rather than edge-first; a released point curls off its facade and settles at a random position inside the scan's bounding box, where it keeps drifting. At 100% the reconstruction is a uniform random cloud — the same 224,979 measurements with all their structure removed — and pulling the slider back reassembles it exactly. Luminous draws points additively, so dense structure blooms and nothing hides anything. Solid uses depth testing and opaque points, which reads closer to a photograph.

Lineage

A study in the language of scan-based installation work — most directly Ryoichi Kurokawa's decomposing point-cloud landscapes and architecture, and Refik Anadol's data sculptures built from photographic archives of cities. It is not a recreation of any specific work, and it is not affiliated with either studio.

Data

The bundled scan is an AliceVision SfM export (Alembic, December 2019): 224,979 points and 251 camera poses of a downtown high-rise block, reconstructed from frames of an aerial fly-over. It was supplied to this project as a sample file; the original author and the source footage are not recorded here.

Limits

  • Sparse reconstruction: glass curtain walls, sky and untextured surfaces have few or no points. That's a property of feature matching, not a rendering choice.
  • No metric scale. Units are whatever the solver chose, rescaled to fit the stage.
  • The Alembic reader handles the Ogawa layout only (not old HDF5 archives), reads the first time sample, takes P from Points or PolyMesh objects, and ignores parent transforms — fine for Meshroom exports, not for arbitrary animated scenes. PLY: ASCII or binary little-endian, vertex x y z with optional red green blue.
  • Up to a few million points is fine on a desktop GPU; on phones use 25–50%.
